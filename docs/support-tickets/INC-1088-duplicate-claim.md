# INC-1088: Claim submitted twice after timeout

| Field | Value |
|---|---|
| Reported by | Marcus Feld, Revenue Cycle Operations |
| Date reported | 2026-03-03 |
| Severity | SEV-2 (High) — duplicate payer submission |
| Environment | Production; clearinghouse integration |
| Component | Revenue cycle / claim submission |
| Status | Open |

## Summary

The clearinghouse accepted a claim, but the API response timed out before it
reached the platform. The submission was retried, and the clearinghouse created a
second receipt. The local claim recorded only the second external identifier.

## Steps to reproduce (as reported)

1. Submit a claim to the clearinghouse.
2. Have the vendor accept the claim but not return a response within the client
   timeout (the connection is dropped after acceptance).
3. Retry the submission (biller re-click or an automated retry).
4. Observe two receipts on the payer side for the same claim.

## Observed

- Two receipts exist at the payer for one claim.
- The local claim shows a single external id — the one from the second
  submission. There is no local record of the first accepted submission.

## Expected

A retry after an ambiguous timeout should not produce a duplicate claim at the
payer. The platform should be able to recognize that the original submission was
already accepted.

## Impact

Billing manually voided the duplicate. Duplicates create payer rework, risk
duplicate-claim denials, and in edge cases affect timely-filing tracking.
Clearinghouse support recommends sending a stable customer request identifier on
retries.

## Preliminary engineering note (tentative)

`submitClaim` (`src/revenue-cycle/claim-service.ts`) writes the submission attempt
and updates the claim only after the vendor call returns, so a timeout after
vendor-side acceptance leaves nothing recorded locally and the claim stays
`READY`. The request id generated by `src/revenue-cycle/clearinghouse-client.ts`
includes a timestamp, so a retry is not recognized by the vendor as the same
submission. Both observations are consistent with the report but need
confirmation against production logs, including the exact timeout window in use.
